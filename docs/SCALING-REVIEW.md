# Scaling, Redis, queue and load-test notes

This software is **not certified for thousands of simultaneous users or sends**. Redis cannot by itself make a server, MongoDB, SMTP provider or network unlimited. Use production-like staging, an agreed workload (concurrent users, recipients per minute, provider limits and target latency), soak/failure/load tests, alerts, backups and independent security review before production. Budget for API, worker, MongoDB Atlas, Redis/Upstash and SMTP connection/throughput limits; cap and increase worker concurrency gradually. Monitor API latency/error rate, event-loop lag/RSS, Mongo pool/primary, Upstash errors/latency, queue oldest-job age/backlog/failed jobs and SMTP response rates. Do not send test email to uninvolved recipients.

Current architecture: Upstash Redis REST executes atomic Lua shared rate buckets when `RATE_LIMIT_BACKEND=upstash`. The persistent job queue/outbox still uses MongoDB; **BullMQ is not installed**. A safe BullMQ migration requires a Redis TCP/TLS endpoint compatible with BullMQ, a tested migration and reconciliation of existing MongoDB jobs, persistence/eviction decisions, idempotency, security review, a rollback and a coordinated cutover. REST credentials alone are not a BullMQ connection. No in-flight queue migration occurs automatically and old jobs must not be deleted.

Redis outages fail closed: no send happens without a reservation. Affected jobs wait and retry without exhausting attempts, including configuration errors; monitor and repair the cause. The public contact endpoint also uses the configured shared limiter. `npm run redis:check` checks PING plus a small TTL-protected multi-key Lua write/read/delete, not sustained capacity. Different instances must all use the same Redis database and settings. Clustered Redis that rejects keys in different hash slots is not supported without a carefully planned bucket-key migration; verify with the diagnostic. During a coordinated switch from Mongo buckets, stop senders because Redis starts with full buckets. Keep keys in backend environments only. Redis eviction/flush/failover loss can reset limits; plan non-evicting persistence, alerting, and provider-side hard quotas.

To scale API and workers independently set `RUN_EMBEDDED_WORKERS=false` on API-only processes and start `npm run workers` on dedicated worker processes. Both use the same MongoDB and Redis settings. Embedded workers remain enabled by default for backward compatibility. Each worker process runs its own scheduler sweep and queue lanes; multiple instances increase both capacity and MongoDB load. The default concurrency is 1 lane **per queue per process**, poll interval 2s. This is not a capacity recommendation. Public contact limits use the client IP observed by Fastify: configure `TRUSTED_PROXY_IPS` only with controlled proxy IPs/CIDRs and test the full proxy chain; never trust untrusted clients' forwarding headers. If proxy identity is not configured, visitors behind it may share one limit.

Concurrent sending uses a conditional recipient claim. Once the external provider call may have happened, an error leaves the recipient `delivery_unknown`, or `sending` if the database itself failed, instead of blindly requeueing. Review provider history before any retry; an automatic exactly-once guarantee is impossible with ambiguous SMTP outcomes. Provider acceptance is recorded as sent, not proof of inbox delivery. Campaign reservation/launch/intake are not fully atomic, and other quota dimensions and calendar rollover remain incomplete. Contact notification retries are at-least-once, so duplicate notification emails are possible after an ambiguous SMTP failure.

## Local narrow simulation (not production capacity)

On an isolated local development environment, 1,000 concurrent rate-limiter calls were sent through a mocked REST transport to a real local Redis server: 100 accepted and 900 rejected against a capacity of 100, in about 196 ms total (p95 about 118 ms). Redis outage was tested to fail closed. A second test enqueued and processed 1,000 no-op jobs against a local single-node MongoDB replica set with 8 worker lanes in about 14.8 seconds; no real email or end-user HTTP load was involved. Hardware, network, database service, dataset and configuration strongly affect results. These are correctness-oriented experiments, not an end-to-end throughput, durability, uptime or crash-free guarantee.
